# Astronomical calculation contract

Dependency: `astronomy-engine` **2.1.19**, MIT, bundled by Vite (no runtime CDN request).

- Official source/documentation: https://github.com/cosinekitty/astronomy/tree/master/source/js
- Method: https://github.com/cosinekitty/astronomy#overview

[`src/astronomy.js`](../src/astronomy.js) exports `DEFAULT_SITE`, `DEFAULT_CONSTRAINTS`, `DEFAULTS`, `normalizeConfig`, `computeNight`, `nightBounds`, `computeYear`, `computeMonth`, `angularSeparation`, and `localDateMs`.

All config fields can be flat: `latitude`, `longitude` (east positive), `elevation` (metres), `timezone` (fixed UTC offset in hours), `zmax`, `sun` (solar altitude threshold), `moon` (minimum separation), `moonMode` (`strict`/`up`/`warn`), `trim` (minutes after/before dark interval edges), `mode` (`LACT`/`LHAASO`). Nested `site` is also accepted, but flat fields override it. Default site is 29.3586111° N, 100.1374972° E, 4410 m, UTC+8. Other schedule settings are preserved by normalization.

Input source coordinates are numeric `ra`, `dec` in degrees, with unique string `id` and optional `name`. Right ascension is 0≤RA<360, declination −90≤Dec≤90. Catalog ICRS positions are treated as fixed J2000 mean-equator directions. The tiny ICRS/J2000 frame bias is neglected (<0.1 arcsec). Proper motion, parallax of fixed sources, annual/diurnal aberration of fixed sources, atmospheric refraction, weather, terrain masking, detector response, slew dynamics, cable wrap, and wobble offsets are not included. Precession and nutation are included via `Rotation_EQJ_HOR`. Sun/Moon use topocentric `Equator` positions with light-time/aberration correction and geometric `Horizon` (no refraction). Lunar separation is between those horizon-frame directions, avoiding mixing catalog-epoch and date coordinates. Azimuth is degrees eastward from north, wrapped to [0,360).

`computeNight(date, sources, config)` is synchronous. It returns `date`, `startMs` (UTC milliseconds), `startHour:18`, `minutes:840`, `step:1`, arrays `sun`, `moonalt`, `moonaz` and aliases `moon_alt`, `moon_az`; each source has `z`, `az`, `sep` arrays. Arrays have **841** entries, including both endpoints. `bounds` is the usable dark interval with trim, or `[0,0]` when there is no darkness; LHAASO uses `[0,840]`. The displayed night is local 18:00 through next-day 08:00. It is intentionally a 14-hour detailed window; at other locations or polar latitudes it may not contain all darkness. Always use daily/year integration for full-day exposure totals. If the UI creates source masks, apply every individual Sun sample as well as the `bounds`, since a single interval cannot describe disjoint darkness.

`computeYear(year,sources,config,onProgress)` returns `{year, days, monthly, daily, step:10, startHour, minutes:1440, mode}`. `days` lists every calendar date, including leap days. `monthly[id]` has 12 values and `daily[id]` has 365/366 values, all in hours. LACT days are local **noon to next noon**, named for the evening date; LHAASO days are local **00:00–24:00**, with Sun/Moon rules and dark-edge trim ignored. Midpoint integration uses ten-minute bins; every calendar day is computed, with no representative-night scaling. This is a geometric time budget, not a weather-adjusted prediction or effective exposure. Individual boundary uncertainty is about one sampling bin. Source angular precision and coarse yearly duration precision are different quantities and should not be conflated.

`computeMonth(year,month,sources,config)` has month=1…12 and returns `{year,month,days,daily,step:10,startHour,minutes:1440,mode}`. It uses the identical daily method as annual totals.

`visibility-worker.js` accepts `{id,type:'year',year,sources,config}` or `{id,type:'month',year,month,sources,config}`. Progress messages are `{id,type:'progress',done,total,percent}`; completion is `{id,type:'result',result}`; errors are `{id,type:'error',error}`. To cancel stale work, terminate and recreate the worker; check the message `id` in the UI. Vite usage: `new Worker(new URL('./visibility-worker.js', import.meta.url),{type:'module'})`.

Computations share one frame rotation and one pair of solar/lunar positions per sample, then evaluate fixed catalog vectors using dot products. There is no expensive ephemeris evaluation per source.

Validation during development compared all 841 minute samples for four sources on three nights (2026-09-22…24) against the original Astropy `builtin` ephemeris fixture at the notebook site, pressure=0. Maximum differences: source zenith **0.00545°**, azimuth **0.02146°** (coordinate-sensitive near zenith), lunar separation **0.00451°**, Sun altitude **0.00039°**, Moon altitude **0.00204°**. Night visibility differs by at most two minutes in those full-fixture checks.

The repository retains an unmodified subset of the Astropy outputs, every 30 minutes including both endpoints, in [`tests/astropy-reference.json`](../tests/astropy-reference.json). `npm test` runs [`tests/astronomy.test.js`](../tests/astronomy.test.js) against this compact fixture, so a clean clone needs no Python or Astropy installation. Tolerances are 0.02° for source zenith, 0.08° for azimuth, 0.04° for lunar separation, and 0.03° for Sun/Moon altitude. The compact fixture does not measure one-minute visibility-boundary agreement. Additional executable checks cover invalid dates, leap day, year rollover, polar daylight, continuous LHAASO exposure, annual/monthly consistency, and agreement of ten-minute and one-minute integration within two coarse bins. These checks validate the implemented planning approximation; they do not validate telescope command execution.

The website uses LHAASO mode for annual and daily source visibility only. Its night scheduling workspace always uses LACT constraints, because the generated source-tracking plan applies to the pointing telescope workflow.
